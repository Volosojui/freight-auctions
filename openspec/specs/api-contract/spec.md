# api-contract

## Purpose

Типобезопасный слой доступа к API аукционов: построение запроса списка из фильтров, вызов четырёх эндпоинтов и валидация запросов/ответов строго по контракту OpenAPI. Даёт остальным фичам единый способ обращаться к данным.

## Requirements

### Requirement: Контрактные модели покрывают DTO схемы

Слой SHALL предоставлять Zod-схемы и выведенные из них TS-типы для всех DTO из `openapi.auctions.v0.json`: элемент списка, детальную, ставку и все enum'ы. Каждый enum MUST включать значение `Unknown`, а неизвестное входящее значение MUST безопасно приводиться к `Unknown`, а не приводить к падению. Nullable-поля контракта MUST моделироваться как nullable.

#### Scenario: Неизвестное значение enum

- **WHEN** ответ содержит значение enum, отсутствующее в известном наборе
- **THEN** схема приводит его к `Unknown` без выброса ошибки

#### Scenario: Nullable-поле отсутствует или null

- **WHEN** nullable-поле (например, цена `current` или `last_bet`) приходит как `null` или отсутствует
- **THEN** валидация проходит, а поле представлено как `null`

### Requirement: Request builder для списка аукционов

Слой SHALL строить тело запроса `POST /auctions/list` из объекта фильтров и параметров пагинации согласно `AuctionListRequest`. Пустые/неустановленные фильтры MUST опускаться (не отправляться как пустые значения). Массивные фильтры (статусы, типы аукциона, id) MUST сериализовываться как массивы; даты MUST соответствовать формату ISO 8601 со смещением из схемы.

#### Scenario: Опускание пустых фильтров

- **WHEN** builder получает объект, где заданы только `page`, `per_page` и `cargo_num`
- **THEN** тело запроса содержит только эти поля и не содержит остальных фильтров

#### Scenario: Сериализация массивных и датовых фильтров

- **WHEN** заданы `statuses`, `auc_type` и диапазон дат погрузки
- **THEN** массивы сериализуются как массивы, а даты — строками в формате ISO 8601 со смещением

### Requirement: Типобезопасные вызовы четырёх эндпоинтов

Слой SHALL предоставлять функции для `POST /auctions/list`, `GET /auctions/{auctionUuid}`, `GET /auctions/{auctionUuid}/bets` и `POST /auctions/{auctionUuid}/bets`. Успешный ответ MUST валидироваться соответствующей Zod-схемой перед возвратом вызывающему коду.

#### Scenario: Успешный ответ списка

- **WHEN** вызвана функция списка с валидными фильтрами
- **THEN** возвращаются провалидированные элементы и `meta` пагинации согласно контракту

#### Scenario: Ответ детальной страницы

- **WHEN** вызвана функция детальной страницы с идентификатором аукциона
- **THEN** возвращается провалидированный объект детальной страницы со всеми обязательными секциями (`main`, `organizer`, `contacts`, `cargo`, `trading`, `payment`, `routes` и т.д.)

### Requirement: Единый разбор ошибок API

Слой SHALL распознавать формат ошибок API: `ProblemDetail` (`code`/`title`/`message`) для бизнес- и HTTP-ошибок и `ValidationProblem` (`code: validation_failed` с массивом `errors[]`) для ответа 422. Разобранная ошибка MUST быть доступна вызывающему коду в типизированном виде, сохраняя `code`, `message` и, для 422, полевые ошибки `errors[]`.

#### Scenario: Бизнес-ошибка

- **WHEN** эндпоинт отвечает ошибкой в формате `ProblemDetail`
- **THEN** вызывающий код получает типизированную ошибку с `code`, `title` и `message`

#### Scenario: Ошибка валидации 422

- **WHEN** `setBet` отвечает статусом 422 с телом `ValidationProblem`
- **THEN** вызывающий код получает `code: validation_failed` и список полевых ошибок `errors[]` (`field`, `message`, опционально `code`)

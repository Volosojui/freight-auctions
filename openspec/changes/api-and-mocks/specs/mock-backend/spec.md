## Purpose

Stateful in-memory MSW-бэкенд, заменяющий реальный сервер: держит сид-данные аукционов и ставок, словарь городов и обслуживает read-эндпоинты в точном соответствии с контрактом — с пагинацией, `meta` и применением фильтров.

## ADDED Requirements

### Requirement: In-memory store с сид-данными

Мок-бэкенд SHALL держать единый in-memory store с детерминированным сид-набором аукционов и связанных ставок, а также словарём городов для `load_city`/`unload_city`. Store MUST быть единственным источником состояния моков; чтения MUST отражать текущее состояние store.

#### Scenario: Детерминированный сид

- **WHEN** приложение стартует с моками
- **THEN** store содержит стабильный набор аукционов и ставок, покрывающий разные типы, статусы и торговые статусы пользователя (включая случаи со скрытыми данными)

#### Scenario: Словарь городов

- **WHEN** фиче нужен список городов погрузки/выгрузки
- **THEN** мок-бэкенд предоставляет фиксированный словарь городов, согласованный с сид-данными аукционов

### Requirement: Список аукционов с пагинацией и фильтрами

Хендлер `POST /auctions/list` SHALL возвращать элементы из store с корректной пагинацией и объектом `meta` (`current_page`, `last_page`, `per_page`, `total`, `from`, `to`), соответствующим запрошенным `page`/`per_page`. Хендлер MUST применять переданные фильтры (как минимум `cargo_num`, статусы, `auc_type`, города, диапазоны дат и цены, `is_available`, `is_bidder`), сужая набор результатов.

#### Scenario: Пагинация

- **WHEN** запрошена страница 2 при `per_page = 20`
- **THEN** возвращаются элементы соответствующего среза, а `meta` отражает `current_page`, `per_page`, `total` и `last_page`

#### Scenario: Применение фильтра

- **WHEN** передан фильтр по `cargo_num` или статусу
- **THEN** возвращаются только соответствующие фильтру аукционы, а `meta.total` отражает суженный набор

#### Scenario: Пустой результат

- **WHEN** фильтры не совпадают ни с одним аукционом
- **THEN** возвращается пустой список и `meta` с `total = 0`

### Requirement: Детальная страница и ставки из store

Хендлер `GET /auctions/{auctionUuid}` SHALL возвращать детальный DTO аукциона из store, а `GET /auctions/{auctionUuid}/bets` SHALL возвращать его ставки. Для несуществующего идентификатора хендлеры MUST отвечать 404 в формате `ProblemDetail`. Флаг `hide_bets_history` MUST быть согласован между детальной и списком ставок.

#### Scenario: Детальная существующего аукциона

- **WHEN** запрошена детальная по идентификатору из store
- **THEN** возвращается полный детальный DTO, соответствующий контракту

#### Scenario: Несуществующий аукцион

- **WHEN** запрошена детальная или ставки по неизвестному идентификатору
- **THEN** возвращается 404 с телом `ProblemDetail`

#### Scenario: Скрытая история ставок

- **WHEN** у аукциона `hide_bets_history` истинно
- **THEN** это отражено в детальном DTO, и список ставок согласован с этим флагом

### Requirement: Контур эндпоинта установки ставки

Хендлер `POST /auctions/{auctionUuid}/bets` SHALL принимать тело `SetBetRequest` и отвечать по контракту: 200 при валидном запросе, 404 для несуществующего аукциона, 422 в формате `ValidationProblem` при нарушении валидации. Полное изменение состояния store (цена, торговый статус, список ставок) реализуется в change `place-bet`; на этом этапе хендлер MUST соблюдать контур статусов и форматов.

#### Scenario: Валидный запрос ставки

- **WHEN** отправлен валидный `SetBetRequest` для существующего аукциона
- **THEN** хендлер отвечает статусом успеха согласно контракту

#### Scenario: Невалидная ставка

- **WHEN** отправлено тело, нарушающее валидацию (например, `price <= 0`)
- **THEN** хендлер отвечает 422 с телом `ValidationProblem` и полем `errors[]`

## Context

`bootstrap-app` завёл пустой `shared/api/mock` и MSW-воркер. Контракт зафиксирован в `docs/openapi.auctions.v0.json` (4 эндпоинта, ~50 схем, все enum с `Unknown`, двойные цены НДС/без-НДС, `ProblemDetail`/`ValidationProblem`). См. `proposal.md` — Why. Этот change отвечает за перевод контракта в код и за stateful-моки; UI не трогаем.

## Goals / Non-Goals

**Goals:**
- Один источник истины типов — Zod-схемы, из которых выводятся TS-типы (`z.infer`), чтобы валидация и типы не расходились.
- Request builder и разбор ошибок покрыты unit-тестами (чистая логика — по ТЗ).
- MSW-store как единый мутируемый источник, готовый к расширению мутацией в `place-bet`.

**Non-Goals:**
- UI, ViewModel-мапперы страниц (живут в фиче-change'ах, хотя мапперы тоже пойдут под unit-тесты там).
- Полная бизнес-логика пересчёта цены/статуса после ставки (→ `place-bet`).
- Кодоген из OpenAPI как отдельный конвейер сборки (решение ниже).

## Decisions

**Zod как источник типов.** Пишем Zod-схемы вручную по OpenAPI и выводим типы через `z.infer`. Ручное написание, а не автоген из OpenAPI: схема небольшая и стабильная («источник правды кандидату»), ручной контроль точнее ложится на nullable/`Unknown`/двойные цены и не тянет тяжёлый тулчейн. _Альтернатива:_ `openapi-zod-client`/`orval` — отклонено как избыточное для 4 эндпоинтов и хуже управляемое по edge cases.

**Обработка `Unknown` в enum.** Каждый enum — `z.enum([...])` с `.catch('Unknown')` (или preprocess), чтобы неизвестное значение из ответа не роняло парсинг, а приводилось к `Unknown`. Это прямое требование контракта (все enum содержат `Unknown`).

**Расположение по FSD.** Весь «провод» — в `shared/api`: сырые контрактные Zod-схемы и выведенные типы (`shared/api/contract`), транспорт (fetch-клиент, request builder), функции эндпоинтов и моки (`shared/api/mock`: store, seed, словарь городов, хендлеры). Причина: `shared` — самый нижний слой FSD и не может импортировать «вверх» из `entities`; при этом mock живёт в `shared/api/mock` (зафиксировано в `bootstrap-app`) и должен типобезопасно порождать контрактные данные, а функции эндпоинтов — валидировать ответы теми же схемами. Поэтому сырой контракт принадлежит `shared/api`. Слой `entities` в этом change не наполняется — доменные ViewModel-мапперы строятся ПОВЕРХ контрактных типов уже в фиче-change'ах (`auctions-list`, `auction-detail`, `bets-view`). Правило зависимостей: `entities` → `shared/api`, не наоборот.

**Валидация ответов.** Каждая функция эндпоинта прогоняет ответ через Zod `.parse`; ошибка схемы = дефект мока/контракта, всплывает в dev громко. В тестах это же даёт контрактную проверку хендлеров.

**Разбор ошибок.** Единый парсер: по телу различаем `ValidationProblem` (есть `errors[]` / `code: validation_failed`) и `ProblemDetail`. Возвращаем типизированный объект ошибки (discriminated union), который фичи (особенно `place-bet`) раскладывают на toast и полевые ошибки формы.

**MSW-store.** Простой модуль-синглтон с массивами аукционов и ставок + индексами по uuid, плюс словарь городов. Сид — детерминированная фабрика (без `Math.random`/`Date.now` в рантайме моков, чтобы данные были стабильны между перезапусками и тестами; вариативность — через фиксированные фикстуры). Фильтрация и пагинация — чистые функции над store (тоже тестируемы). `setBet`-хендлер на этом этапе соблюдает контур статусов, но не мутирует агрегат (мутация — в `place-bet`).

## Risks / Trade-offs

- [Ручные Zod-схемы могут разойтись с OpenAPI] → Валидация ответов моков теми же схемами + контрактные unit-тесты на форму ответов ловят расхождения рано.
- [Сид-данные не покроют edge cases фич] → Осознанно закладываем в сид разнообразие: типы аукционов, статусы, `can_set_bet` true/false, `hide_bets_history`, `hide_points_address_and_contacts`, `no_view_cargo_price`, наличие/отсутствие своей ставки, пустой список ставок.
- [Двойные цены (с НДС/без) легко перепутать] → В схемах и фикстурах держим оба поля явно и согласованно; в фичах не вычисляем НДС на клиенте, а берём готовые поля контракта.
- [Store как синглтон усложняет изоляцию тестов] → Экспортировать `reset()`/фабрику store для тест-сетапа, вызывать между тестами.

## Open Questions

- Формат ответа `setBet` в контракте описан как «проксируется от upstream» (200 без явной схемы тела). Точную форму тела успешного ответа фиксируем в `place-bet` вместе с мутацией; на форму специй текущего change это не влияет.
